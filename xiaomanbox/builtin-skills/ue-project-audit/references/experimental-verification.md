## 1. 为什么资产结构诊断不够

`references/performance-diagnosis.md` 能把"卡"归因到"SM_Grass2 摆了 19,812 份、没开
Nanite、占本次统计 53% 三角形"——这是**推断**：占比高、配置有问题，所以大概率是它。
推断可以指方向，但不是证据。用户要看到的是**删了它，帧率真的变了**这种因果关系，
口说无凭。这份文档就是怎么把推断变成一组"改之前、改之后"的对照数字。

## 2. 硬规则：永远不在原始关卡上做实验

做这类实验前**必须先取得用户明确同意**——这不是审计范畴内的只读操作，是要删/藏关卡内容
的实验，哪怕对象是一份副本。同意要一次性覆盖整个实验方案（见 §8），不是走一步问一步。

不管拿没拿到同意，第一步永远是复制：任何隔离操作都只发生在测试副本上，原始关卡文件
不允许被这套流程改动一个字节。

## 3. 协议：复制 → 基线 → 假设 → 隔离 → 重测 → 对比

```
0. ue_get_current_level                      记下原始 package 路径，后面要用它切回去
1. ue_save_level({ path: 测试副本路径 })       另存为一份新文件——存完之后当前编辑的
                                              就是这份副本，原文件已经定住不再变
2. ue_capture_perf_trace(duration_seconds)   基线测量，记下 FrameTime/GPU 等关键数字
3. 挑一个假设（来自资产结构线索里占比最高的那个嫌疑对象）
4. 应用隔离（§4）
5. ue_capture_perf_trace(相同 duration_seconds)   重测——采样条件要和基线一致
                                              （同样在不在 PIE、镜头位置/路径相同），
                                              条件不一致，对比就没有意义
6. 算差值：FrameTime/avg_fps/GPUTime 变了多少，变了百分之多少——这才是能写进报告的证据
7. 假设成立（改善明显）→ 报告结论
   假设不成立（几乎没变化）→ 排除这个嫌疑，换下一个假设回到第 3 步，
   或者嫌疑对象不止一个时升级到二分法（§6）
8. 收尾（§7）
```

测试副本路径建议放 `/Game/_PerfTests/` 这样一眼能看出是临时产物的目录下，
不要和用户真正的关卡混在一起。

## 4. 隔离手段怎么选：先能不能可逆，再谈删不删

**先用隐藏，能回答大部分问题：**

```
ue_set_property({ targets: { filter: { class: "嫌疑类名" } }, properties: { "bHidden": true } })
```

隐藏是可逆的（改回 `false`，或者干脆放弃这份副本），但只测得到**渲染成本**——隐藏的
Actor 默认还在 Tick、还在做物理模拟，测不出那部分开销。批量套用前先在**一个**目标上
验证 `bHidden` 这个属性名真的解析得对（用 `ue_get_actor` 的 `properties` 参数读一次），
别对着几百个 Actor 广播一个可能写错的属性名。

**怀疑成本不只在渲染时（大量 Tick、物理模拟），才用删除：**

```
ue_destroy_actor({ targets: { filter: { class: "嫌疑类名" } } })
```

删除测得到全部成本，代价是这一步在副本上也是不可逆的——副本本来就是消耗品，这个代价
可以接受，但依然要在开始实验时跟用户说清楚会用到这一步。

## 5. 已知的工具边界：Foliage 删不掉

`ue_destroy_actor` 自带一份保护名单，`InstancedFoliageActor` 在里面——**批量删除会被
拒绝**，不管是不是在测试副本上。如果嫌疑对象是靠 Foliage 工具铺的植被（不是手摆的
Instanced Static Mesh Actor），这条路走不通。

如实告诉用户："这批是用 Foliage 工具铺的，我这边的删除工具对它有保护、动不了——
需要你自己在 Foliage 面板里把这个类型的密度降下来，降完告诉我，我再重新测一次。"
不要绕开保护机制去找别的删除路径，那道保护是用来防误删的，不是这个实验的绊脚石。

## 6. 二分法：嫌疑对象不止一个、又分不出主次的时候

单点排除（§3 的默认流程）在嫌疑对象唯一或者占比压倒性时最快——用户这次的真实 case
里 SM_Grass2 占了 53% 三角形，直接测它一个就够，不需要二分法。

只有当好几个嫌疑对象占比接近、说不清主次时，才用真正的二分：

1. 把候选嫌疑分成两半（按类型，或者按关卡里的空间区域）。
2. 隔离其中一半，测一次。
3. 性能显著回升 → 元凶在被隔离的那一半，把这一半再分两半，重复第 2 步。
4. 性能几乎不变 → 元凶在没动的那一半，反过来对这一半重复第 2 步。
5. 每轮把候选范围减半，通常 3–4 轮能从几十个嫌疑收敛到 1–2 个具体资产——比一个一个
   试快得多，这也是二分法本来要解决的问题。

## 7. 收尾：三件必须做的事

1. **切回原始关卡**：`ue_open_level({ path: 原始路径, force: true })`。`force: true`
   是必须的——当前副本上还留着我们自己做的测试改动，那些改动本来就该被丢弃，
   不是真的需要保护的用户工作。
2. **问用户要不要清理测试副本**（`ue_content_delete`）。别默认帮它做删除决定，
   也别默认放着一堆 `_test_...` 文件不管——两种默认都是替用户做了他没让做的选择。
3. **报告里写清楚这是在关卡副本上做的对照实验**，不是对原始关卡的改动。用户看到
   "删除了 xxx" 字样容易紧张，说清楚删的是哪一份文件能省掉一次不必要的心跳。

## 8. 操作纪律

- 实验开始前**一次性**讲清楚整个方案：复制哪张关卡、要验证什么假设、大概要跑几轮、
  完成后会做什么——拿到用户对"整个实验"的同意，而不是删一个问一次要不要继续。
- 各步隔离操作依然会各自触发系统审批（`destroy_actor` / `set_property` / `save_level`
  都是已有的风险分级）——那是执行层面的确认，跟"要不要开始整个实验"是两件事，不冲突，
  不用因为"已经同意过实验方案了"就想办法绕过它们。
- 中途发现假设错了、想换个方向，要跟用户说一声再继续——不要不声不响地在同一份副本上
  无限试验，试到最后连自己是从哪个状态开始的都说不清，那样产出的数字同样不可信。
