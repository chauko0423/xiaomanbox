# 帧边界与时间

**不要自己推算帧边界。** UE 内部这件事本身就不一致，靠记忆推算的结果是错帧，
而错一帧就是穿帮 —— 而且是那种渲完才发现的穿帮。

## 四条互相打架的规则

| 场景 | 规则 |
|---|---|
| Sequencer 的段（section） | 起始帧**含**，结束帧**不含** —— `[start, end)` |
| Movie Render Queue 渲染 | **不含末帧**。0–50 的序列出 0–49，共 50 帧 |
| AnimSequence | 首尾**都含** |
| FBX 导入的动画段 | 尾后带一点数据，末帧被完整包含；**但一旦裁剪过又变回排他** |

还有一条：**播放头正好压在两段交界上时，显示的是后一段的数据。**
排查「这一帧为什么是这个画面」时，先确认播放头在哪一侧。

## `sequence_describe` 的约定

所有段的范围一律按 **`[start, end)`** 上报，返回的文本里也这么写。
拿到 `[0, 300)` 就是 0 到 299 共 300 帧。

## 无缝循环（turntable / 环绕）

做 360° 循环时，如果按「首尾都含」去算，**接缝处会重复一帧** ——
在 loop 播放的产品图上一眼能看出卡顿。

正确算法：N 帧一圈，关键帧打在第 `0` 帧（0°）和第 `N` 帧（360°），
播放范围设 `[0, N)`。第 N 帧的存在是为了让插值正确，但它不会被渲染出来 ——
这正是「结束帧不含」在这里帮了忙。

## 两套时间轴：display rate vs tick resolution

序列内部有两个帧率：

- **display rate** —— 用户看到的（24 / 25 / 30 fps）
- **tick resolution** —— 内部存储精度（常见 24000）

Python API 在不传 `time_unit` 时**按 tick resolution 解释**，
于是「第 10 帧」会变成 0.0004 秒 —— 静默偏差 800 倍。

`sequence_describe` 返回的所有帧号都是 **display frame**，
并会回报它实际用的 `display_rate`。**引用帧号时以它为准。**

## 改帧率是危险操作

改 tick resolution 时，如果新值不是旧值的整数倍，
**段边界和关键帧会被 round 掉** —— 这是静默数据损坏，不是可回滚的编辑。

改 display rate（24 → 25）也不是所有东西都能等比缩放：
音频、已烘焙的动画资产、物理模拟各有各的行为。

**这件事必须由用户明确发起并确认，不能作为其他操作的副作用。**
用户说「换成 25fps」时，先说清楚会影响什么，再让他决定。
