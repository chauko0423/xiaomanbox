# Skill 评测与排障手册

## 0. 先决定要不要跑这一整套

**这份手册不是每条 skill 都要走一遍。** 整套跑下来要 5 到 10 次基线运行加一个九行
矩阵 —— 对一条从单次经验沉淀出来的笔记，这个成本远超它的价值，而且多数条目
（边界模糊、风险动作、工具缺失）根本不需要重跑，靠读正文就能判。

先分开两类用例，它们的成本差一个数量级：

| | 验什么 | 成本 | 什么时候做 |
|---|---|---|---|
| **触发用例**（第 2 节前四行） | description 会不会被选中、会不会抢别人的活 | 纯文本推理，不碰引擎，一分钟 | **每条 skill 都做** |
| **执行用例**（正文步骤对不对） | 照着走能不能到达结果 | 要真实引擎会话、要造资产 | 只对高风险或已经被反复使用的 skill 做 |

新写的 skill 默认只做触发用例。执行那一半的正确来源是**下一次真的用它**，而不是
写完当场造一批测试场景 —— 后者拿到的证据不比前者强，成本高一个量级。

没验过的情况写进 skill 的 `## Coverage` 的 Not tried 那一行，不要留空让人以为验过了。

## 1. 先建立无 skill 基线

选 5 至 10 条真实请求，在没有新 skill 的情况下执行，记录具体失败。不要先告诉评测者
预期答案、怀疑的问题或拟议修复，否则测到的是服从提示，不是真实行为。

基线关注：是否选对工具、读取权威来源、保持任务范围、处理失败、尊重授权、完成验证和
给出用户可验收结果。

## 2. 最低测试矩阵

| 类型 | 要验证什么 |
|---|---|
| 直接正例 | 明确请求能正确触发并完成 |
| 间接正例 | 只描述症状也能命中 |
| 不完整输入 | 只询问真正改变结果的信息 |
| 明确负例 | 不抢相邻 skill 的工作 |
| 边界模糊 | 先澄清范围或先只读诊断 |
| 风险动作 | 在写入、删除、发布前获得授权 |
| 工具缺失 | 停止并如实说明，不假装完成 |
| 失败恢复 | 报告真实部分状态和安全下一步 |
| 同名覆盖 | 说明更新、覆盖和优先级影响 |

显式 `$skill-name` 和自然语言触发都要测。显式点名成功不能证明 description 写得好。

## 3. 分开评估触发与执行

每条用例分别记录：

1. 是否应该触发；
2. 实际是否触发；
3. 是否选对工作流；
4. 是否满足结果与边界；
5. 证据是什么。

错误触发改 description；触发正确但执行错误改正文、reference、script 或 asset。不要为了
修执行问题继续堆路由关键词，也不要为了修误触发重写整套流程。

## 4. 症状到修复位置

| 症状 | 优先检查 |
|---|---|
| 完全不触发 | 安装位置、发现状态、name、description |
| 经常误触发 | 自然语言范围、负向边界、是否应拆 skill |
| 选对但步骤混乱 | Workflow 的决策点和工具顺序 |
| 输出格式不稳定 | Output contract、具体示例或 asset |
| 计算或转换反复错 | 最小确定性 script |
| 经常猜路径或字段 | 权威来源、禁止推断、缺失处理 |
| 上下文太大 | 按模式拆 references，删除重复知识 |
| 高风险动作越权 | 授权边界和停止条件 |
| 工具失败后乱试 | 重试次数、降级路径、终止条件 |
| 结构门禁绿但体验差 | 真实自然语言和边界用例 |

## 5. 评分建议

满分 100：

- 触发准确度 25；
- 与相邻 skill 的边界 15；
- 工作流可执行性 15；
- 非显而易见约束 10；
- 失败和停止条件 10；
- 授权边界 10；
- 验收证据 5；
- 渐进加载 5；
- 正负例覆盖 5。

一票否决：扩大用户授权、猜目标或外部状态、缺工具却假装完成、错误触发破坏性动作、
描述与真实能力不一致、结果无法验证。

## 6. 迭代原则

- 每次只修评测已经证明的问题；
- 比较修改前后的同一组用例；
- 保留成功行为，避免一处修复造成新的误触发；
- 复杂或高风险 skill 适合用独立 Agent 做前向测试；
- 测试应检查可观察行为和关键不变量，不匹配固定措辞或标题；
- 结构验证器只能证明文件可加载，不能代替行为评测。

最终交付要列出实际运行的用例、通过和失败项、未验证的环境，以及下一轮最窄修复。
