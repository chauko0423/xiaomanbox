# 触发与边界样例

## 应该触发

- 「把刚才排查黑屏的经验沉淀成一个 SKILL。」
- 「以后再碰到这种蓝图接线错误，Agent 应该按今天这套顺序查。」
- 「给这个重复检查写个脚本，再包装成技能。」
- 「把这份人工 checklist 变成能自动触发的工作流。」
- 「更新我现有的 ue-build-diagnosis，补上这次验证过的失败处理。」
- 「先给我一个 skill 草案，不要写文件。」

## 完成任务后可以主动提案

以下情况可以在正常交付末尾加一句候选提案，但不能直接写盘：

- 同一种失败已经出现多次，并验证出稳定的根因与恢复路径；
- 多个工具必须按固定顺序使用，顺序错误会造成返工或数据风险；
- 用户反复强调同一个项目不变量，且它适用于一类任务；
- 一段机械检查每次都重新编写，适合变成无依赖脚本。

提案示例：

> 这次已经验证出“先审计绑定、再区分未加载与失效、最后才修复”的稳定流程。
> 可以沉淀成 `ue-binding-diagnosis`，包含一个主流程和一组失败样例。要我写进你的
> Skills 目录吗？

## 不应该触发

- 普通任务刚开始，主工作还没有完成；
- 「解释一下刚才做了什么」——这是复盘，不一定是 skill；
- 「记住我喜欢紫色」——这是个人偏好，不是专项工作流；
- 只遇到一次无法复现的报错；
- 结论来自推测，没有工具结果或验收支持；
- 用户拒绝写盘后仍继续调用本地写文件工具；
- 为了“以后可能有用”创建空 references、scripts 或 assets 目录。

## 边界模糊

**「以后都这么做。」** 先确认“这么做”指哪条可复用规则以及适用范围。不要把整次对话
原封不动写进 skill。

**「把内置 skill 改一下。」** 运行中的安装目录不是用户资产。优先在用户 Skills 目录
创建同名覆盖；如果用户正在源码仓库里开发，则按仓库规范修改并跑门禁。

**「你自己看着沉淀。」** 这允许提出候选，不等于允许写磁盘。先交付当前任务和候选摘要，
得到确认后再创建文件。

**「给我做一个万能 UE skill。」** 先拆成可识别的用户目标。触发、输入和验收标准不同的
工作流不能塞进一个总入口。

## 失败处理

- 没有目标目录：让用户从 **设置 → AI → 打开 Skills 目录** 获取路径，不猜目录。
- 目标 skill 已存在：读完后说明将更新哪些部分，不覆盖未读内容。
- 写入被拒绝：保留为聊天中的完整草案，不重试审批。
- 没有 shell：仍可创建 Markdown 和脚本，但明确脚本没有实际运行。
- 校验失败：只修失败项；不要删除资源或放宽规则来换取通过。
