## 1. 心智模型

好 skill 不是超长提示词，也不是领域百科。它把通用 Agent 变成知道本地规矩、会走正确
路径、懂得何时停止的专职执行者。

最有价值的内容是：

- 容易选错的工作边界；
- 不明显但必须遵守的项目不变量；
- 工具调用顺序和分支条件；
- 禁止猜测的数据；
- 失败后的恢复或停止方式；
- 用户可观察的验收标准。

三层信息各司其职：

1. `name + description` 决定会不会被选中；
2. `SKILL.md` 决定选中后如何行动；
3. `references/`、`scripts/`、`assets/` 只在对应分支按需加载或使用。

不要把“知识越多”当质量。只保留会改变决策、降低错误或提高可验证性的内容。

## 2. 与其它能力的边界

| 资产 | 负责什么 |
|---|---|
| 项目规则文件 | 全仓长期、普遍适用的约束 |
| skill | 某类任务命中后才加载的专项工作流 |
| MCP / 工具 | 实时数据、认证、授权和受控动作 |
| script | 重复且确定的机械处理 |
| reference | 只在特定分支需要的详细知识 |
| asset | 最终要复制、填写或改造的模板与骨架 |
| plugin | 分发一个或多个 skill 与连接能力 |

工具提供手和眼睛，skill 提供做事方法。不要在 skill 里假装一个不存在的工具，也不要用
大段自然语言模拟本该由确定性脚本完成的逐字符处理。

## 3. 从真实工作提炼经验

先完成任务，再提炼。推荐先在没有新 skill 的情况下观察真实工作，记录具体失败：

- 选错工具或相邻流程；
- 顺序错误造成返工；
- 猜字段、路径、版本或资源状态；
- 忘记读取权威来源；
- 修改范围过宽；
- 工具失败后继续乱试；
- 技术完成但没有可验收交付；
- 不该触发时抢了别的 skill。

只针对已经观察到的失败或已经验证的成功路径写规则。不要先写一大篇“可能有用”的文档，
再寻找它能解决的问题。

经验进入 skill 前要通过四个过滤器：

1. **有证据**：来自真实文件、工具输出、成功修复或验收。
2. **可复用**：去掉本次专属名称和路径后仍然成立。
3. **非显然**：没有这条信息，Agent 很可能做错或走弯路。
4. **有边界**：知道适用条件，也知道什么时候不成立。

一个偶发错误不能直接升级成永久铁律。区分根因、当时的补救措施、用户偏好和普遍规则。

## 4. 定义唯一成果和范围

先完成这句话：

> 当用户提出某类请求时，交付某个可观察结果。

如果一句话里包含多个触发方式、不同输入、不同风险或不同成功标准，应拆成多个 skill。

然后列出相邻能力：

- 哪些请求应该由它接手；
- 哪些只做解释或审计，不应实施；
- 哪些属于发布、删除、部署或其它高风险流程；
- 哪些尚未支持，不能绕道实现；
- 用户只想讨论时，是否会被误判成执行。

一个技能只服务一个可识别的用户目标。不要创建“万能 UE 助手”“处理所有项目问题”这类
没有触发边界的总入口。

## 5. 选择安装位置

先服从用户明确指定的位置和目标宿主。常见选择：

- 当前软件的用户 Skills 目录：个人可覆盖内置 skill，适合本机使用；
- 项目自己的 skill 目录：适合与仓库共享的开发流程；
- 源码仓库的打包资源目录：适合正式随产品交付，必须遵守仓库门禁；
- plugin：适合对外分发、组合多个 skill 或连接器。

不要猜用户目录。没有路径时，让用户从 **设置 → AI → 打开 Skills 目录** 获取。创建前先
列出目录；发现同名项时，明确这是更新、覆盖还是另起名字。

用户 skill、插件 skill、内置 skill 可能存在优先级。同名覆盖是产品行为，不是普通新增，
必须让用户知道。

## 6. 编写 description

`description` 是路由合同，不是使用说明。推荐结构：

```text
[明确能力]. Use when the user asks for [自然语言请求和典型症状]. Do not use for [相邻任务、只读/实施边界或未支持能力].
```

编写原则：

1. 最重要的能力和触发词放前面；
2. 写用户会说的话，不只写内部模块名；
3. 同时说明成果、正向触发和负向边界；
4. 中文用户优先的技能要包含中文自然语言；
5. 不把完整流程、长清单和安全说明塞进 description；
6. 不用“帮助处理项目”“处理 Unreal 问题”这种无法区分邻居的描述；
7. 不声称尚未实现或没有工具支持的能力。

错误示例：

```yaml
description: Helps with Unreal development.
```

改进后：

```yaml
description: Diagnoses build and validation failures in an Unreal project and reports the failing stage with evidence. Use when the user reports a failed build, CI gate, or packaging error. Do not use for implementing unrelated gameplay features or publishing a release.
```

## 7. 编写主流程

主文件只保留决策与执行骨架。可按实际需要选择这些部分：

- Outcome：可观察成果；
- Workflow：从权威输入到验证的最短路径；
- Constraints：不能猜、不能动和必须保留的内容；
- Failure handling：缺输入、工具失败和部分成功时怎么办；
- Escalation：哪些选择或权限必须交给用户；
- Output：最后如何向用户交付。

流程应写清：

1. 输入来自哪个真实来源；
2. 什么条件决定走哪个分支；
3. 哪些工具按什么顺序使用；
4. 哪些动作会修改数据或消耗资源；
5. 如何确认结果，不只相信成功消息；
6. 失败后重试、降级还是停止；
7. 用户最后能看到、打开或运行什么。

删除“认真分析”“确保准确”“遵循最佳实践”等不会改变行为的空话。不要重复教授模型已经
掌握的语言、框架或通用工程知识。

示例要具体，优先输入/输出配对和真实分支；不要用一串形容词描述“专业、优雅、健壮”。

## 8. 渐进加载与资源选择

### references

适合 schema、映射表、平台差异、长排障手册、详细案例和只在某一模式下需要的规则。

主文件要明确路由：

```text
报告显示绑定无法解析时，读取 references/binding-diagnosis.md。
```

不要只写“更多信息见 references”。所有 reference 应由主文件直接提到，不做多层跳转；
长 reference 在开头放目录。

### scripts

适合反复出现、需要确定结果、容易逐字符出错的扫描、转换、校验和索引生成。Agent 和现有
工具能可靠完成时，不要为了显得完整而加脚本。

### assets

适合最终输出模板、报告骨架、固定 Prompt、图片、字体和 starter project。它们是产物素材，
不是指令正文。

每个资源都必须有具体调用方。不要创建空目录、占位文件、重复 quick reference、README、
changelog 或安装说明，除非分发要求明确需要。

## 9. 制作可靠脚本

脚本应满足：

- 目标环境已有运行时和标准库优先；
- 输入参数化，不写死机器绝对路径和项目 ID；
- 清楚说明运行时机、输入、输出、依赖和失败码；
- 预期错误自行处理并给出可行动信息；
- 不读取或写入任务范围外的目录；
- 不嵌入密钥、令牌、个人信息或会过期的在线数据；
- 命名直接表达用途；
- 正常样例和有意义的失败样例都实际运行；
- 没有运行时或 shell 时如实标记未执行。

脚本只是确定性机械层。是否该运行、选择哪些输入、用户是否授权，仍由 skill 的工作流决定。

## 10. 权限、风险与停止条件

调用 skill 只是选择工作流，不是额外授权。区分：

- 只读检查；
- 可逆修改；
- 用户文件写入；
- 删除、覆盖、发布、部署和外部消息；
- 昂贵的渲染、构建或长时间资源消耗。

对需要额外授权的动作，在真正执行前确认，而不是因为用户提到某个技能就默认允许。

重试必须有停止条件。例如只对明显的临时连接错误重试一次；同一错误持续时停止并报告。
不要通过换路径、换工具、削弱验证或改目标来偷偷绕过失败。

缺少重要选择时才问问题。能够从权威文件或只读工具查到的内容不要反问用户。

## 11. 更新现有 skill

更新前读完整主文件和所有将修改的资源。先定位症状：

- 不触发：改 description 或安装发现问题；
- 误触发：缩小范围、补负向边界或拆分；
- 触发正确但步骤乱：改 workflow；
- 输出不稳定：补 output contract、示例或 asset；
- 机械计算反复错：加最小脚本；
- 经常猜数据：明确权威来源和禁止推断；
- 上下文膨胀：拆 references；
- 高风险越权：补授权和停止条件。

修复应保持狭窄。不要为了一个样例追加覆盖所有未来情况的永久规则；不要覆盖用户原有内容、
命名、工具选择和权限策略。

## 12. 内容质量与反模式

常见失败：

1. 写成百科全书，当前步骤反而找不到；
2. description 只有领域名，没有成果和边界；
3. 没有负向边界，与相邻 skill 抢工作；
4. 把一次事故写成普遍规律；
5. 把个人偏好包装成强制约束；
6. 把一个示例固化成唯一流程；
7. 本可三行完成却维护复杂脚本；
8. 需要确定性却每次让 Agent 临场生成；
9. reference 存在但主文件不路由；
10. reference 多层套娃，信息只读到一半；
11. 复制会过期的 API 文档、版本列表和服务状态；
12. 只测试显式 `$skill-name`，不测自然语言；
13. 验证器通过就宣称技能有效；
14. 把技能调用误当成删除、发布或部署授权；
15. 维护第二份硬编码技能清单，而不是读取真实安装注册表。

内容要使用稳定术语。给一个默认做法和必要逃生口，不罗列四五种等价方案让执行者重新选择。

## 13. 完成交付清单

- 名称合法且与目录一致；
- description 有明确成果、正向触发、自然语言和负向边界；
- 主文件只保留执行骨架；
- 每个资源都从主文件直接路由；
- 脚本已运行正常和失败样例，或明确标为未执行；
- 没有密钥、隐私、机器路径和短期事实；
- 写入前获得对应授权；
- 正例、间接正例、不完整输入、负例、相邻技能和失败恢复均已设计；
- 回读磁盘文件并运行目标仓库已有门禁；
- 告诉用户安装位置、触发方式、验证结果和剩余风险。

结构正确只是最低线。真实请求能选对、做对、停对、交付清楚，才算完成。
